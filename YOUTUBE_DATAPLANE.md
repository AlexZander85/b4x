# YouTube dataplane — карта форка (подчинена PROJECT_DIRECTIVES)

Не план кампании L0–L8. Не ABD/WARP. Это **что ТСПУ делает с YouTube**, **что доказано на `.152`**, и **какая архитектура из этого складывается**.

Владелец: живой Keenetic, UX только с телефона `.152`. Агент читает этот файл после `PROJECT_DIRECTIVES.md` и `state_packet`. Не открывать заново закрытые дыры.

Живой слой и sha/md5 — только `.ag/summaries/state_packet.md`.

---

## 1. Идеальная картина (цель форка, не факт на роутере)

YouTube — полигон цикла `monitor → ABD → discovery → canary`. Руками стратегию не подбирать **после** того, как дата-плоскость умеет три формы handshake.

Три независимых пути одного сайта (это не один «обход YouTube»):

```
телефон .152
 ├─ QUIC UDP/443 googlevideo     → тактика A: fake UDP 6/6 (обратный split)
 ├─ TCP короткий CH (youtubei)   → тактика B: fake SNI AutoTTL + combo
 └─ TCP ECH ~1800 B (только youtube-video)
                                  → тактика C (цель, не факт):
                                    classify → HOLD полного record
                                    → один маленький desync в ГОЛОВЕ
                                    → тело как обычный TCP ≤ MSS
                                    НИКОГДА на youtube-ui / youtubei
```

**Формула C (форк, не живой PASS):** desync сидит в голове, тело уезжает как обычный TCP. C — не «нарезать весь ClientHello». C: (1) верно классифицировать flow; (2) собрать полный handshake; (3) одно маленькое решение у начала; (4) остальные байты — MSS-compliant TCP, прямой seq; (5) **fake SNI должен уйти на WAN**, IP-пакет ≤ MTU 1500. Combo — не универсальная кнопка.

Классификатор обязан **до** backoff Cronet повесить на flow один из трёх сетов: API (`combo-timestamp` / `211bf07f`), видео (`youtube-video` / `9b31cb9b`), UI (`youtube-ui`). Без сета любая тактика бьёт мимо.

Когда дата-плоскость стабильна, ABD не изобретает pastseq: он только **переключает** A/B/C (или откатывает слой) по health drop на этих трёх наборах.

Пока тактика C не держит ванильный seek — discovery крутить рано: программа будет крутить timestamp на невыбранном или несобранном CH.

## 2. Что режет ТСПУ (поле, не брошюра)

- TCP 443: тихий дроп по SNI `youtube*` / googlevideo, **без RST**. Нет ответа ≠ «сеть умерла».
- QUIC UDP 443: чаще проходит, если fake UDP ушёл.
- Короткий полный ClientHello (~189 B, `16030100b8`, youtubei): fake SNI + combo **пробивает**.
- Длинный ECH ClientHello (~1740–2100 B): телефон режет MSS `1396+хвост` (`16030106f0` / `0710` / `06d0`). Combo по **первому** куску ломает сборку у сервера. Голый первый кусок (fake-only ACCEPT) отдаёт ТСПУ почти весь CH.
- После сборки полного ECH combo из 12–15 кусков (first-byte + shuffle + 30 мс) **на GGC googlevideo** сервер **не ACK** — `0x17` с клиента нет. Тот же combo на собранный ECH **youtubei / i.ytimg** (holdch3 retest 11:10) интерфейс поднимает — дыра не «любой ECH», а **GGC**.
- DNS UDP/53 с телефона на YouTube: **ноль**. Cronet DoH. `scoped_dns_hints` без видимого DNS инертен.
- **Поле 21.08 (весь день):** на медиа-GGC (74.125.154.106, 173.194.151.66, 74.125.111.166, 172.217.133.166) — **ноль** успешных TLS (`first5=1703`) при сотнях `1603` от трёх устройств (.152 ReVanced+ваниль, .39 ваниль, .44). youtubei на `172.217.114.4` здоров: 199×`1703`, 148×`1403`. Зависает и ReVanced — TCP-fallback Cronet не зависит от приложения. Гипотеза после исчерпания геометрий и fake-методов: **ТСПУ режет TCP к диапазонам googlevideo по IP**, независимо от CH. Решающий дешёвый тест: curl с `.40` `--resolve <rrX---sn-X.googlevideo.com>:443:<ggc-ip>` — если молчит даже с чистым plaintext-SNI CH, тактика C невозможна, жить на A + steering.
- Gmail живёт на тех же Google IP. Красить `172.217.0.0/16` или `offload_policy=exclude` нельзя.

Клиенты:

| Клиент | Старт видео | Seek |
|---|---|---|
| ReVanced | почти всегда QUIC (тактика A) | редко падает в TCP; маркер `returnyoutubedislikeapi.com` |
| Ваниль | QUIC, затем TCP+ECH на тот же или новый GGC | почти всегда тактика C |

`.40` curl ≠ UX. Вердикт — слова владельца про `.152`.

## 3. Архитектура в коде (как должно быть устроено)

Один пакет YouTube проходит четыре узла. Не смешивать с PPE/GUI.

```
NFQUEUE
  → classify (сет + hint)
  → shape  (полный ли TLS record?)
  → hold   (если ECH разрезан — DROP, ждать хвост ≤80 мс)
  → inject (тактика A / B / C)
```

### 3.1 Classify

| Механизм | Файл | Правило |
|---|---|---|
| Три сета по SNI | `b4.json` / `b4.json.exp-dnshint.json` | `youtubei*` ≠ `googlevideo` ≠ UI |
| QUIC→TCP handoff | `src/nfq/quic_handoff.go` | тот же client+MAC, TTL 90 с, proto 6 и 17 |
| googlevideo `/24` | тот же файл + `classifier.IPv4Prefix24` | **только** `*.googlevideo.com`. Не youtubei, не UI (Gmail) |
| TCP SNI тоже пишет handoff | `handler.go` после matchedSNI | соседний сокет на тот же `/24` без SNI в первом куске |
| Сырой hint для hold | `googlevideoSetForHold` | обходит Decide `ECH fallback non-final` / PhasePartial |
| DNS hints | `scoped_dns_hints` | флаг может быть ON; с телефона корма нет |

Не делать: `targets.ip` на google `/16`, global learned-IP, syn_fake «чтобы классифицировать».

### 3.2 Shape

`src/nfq/tls_record.go`: record `0x16`, длина `5+u16`. Если `5+len > payload` — record неполный. Хвост **не** начинается с `0x16`.

Короткий полный `0x16` → сразу inject B. Неполный → hold. Не-`0x16` при живом hold → append.

### 3.3 Hold

`src/nfq/tcp_ch_hold.go`, inject `src/nfq/tcp_ch_hold_inject.go`.

- Ключ: 4-tuple. Store **общий** на все NFQUEUE workers (`runtimeState.chHold`).
- Первый неполный `0x16`: DROP (не на провод), ждать хвост 80 мс.
- Хвост без SNI / без `matched`: всё равно `continueCHHold` (holdch2).
- Нет сета, но есть gv `/24` hint: стартовать hold с этим сетом (holdch3).
- Собрали: rebuild IP/TCP, PSH, один inject.
- Ретрай первого куска после сборки: `hold replay` того же полного CH, не второй hold.
- Timeout: fake-only flush (как rexmit) — это откат, не успех.
- Не путать с `TCPHoldStore` (hold-replay классификатора, ACCEPT без combo). Тот путь при живом handoff **сбрасывает** hold как evidence-confirmed.

## 5. Инварианты деплоя (чтобы не уронить роутер)

- Эксперимент: `$F/bin/b4.exp-<слой>`. Живой `$F/bin/b4` не затирать (там rexmit/rc9).
- `/opt/sbin/b4` — **только** исполняемый live. USB после ребута `noexec`; S99b4 remount exec и копирует **один** файл, если `/opt/sbin/b4` не executable.
- `/opt` = ubi 98 МБ. Вторая копия 17 МБ на `/opt/sbin` роняет b4 (`No space left`, обрезанный бинарь). Архив `.exp-*` только на флешке (27 ГБ).
- Не менять в одном деплое бинарь + PPE + сеты + логи.
- Не `exclude`, не mutation, не GUI `30d4208b`/`43b5042b`.
- Лог: `$F/b4/log/b4.log`. Маркеры seqovl: `hold assembled` → `C-seqovl start … seqovl=681` → сегменты `payload_len=682` `seq_delta=-681`, затем `1396`, затем хвост. Не `C-headmss`, не `combo` на gv ECH. Успех: `first5=17`.

Устройства: `.152` `22:30:F3:33:62:27` (телефон), `.40` `BC:FC:E7:B5:F5:8E` (ПК). Не путать с `.39` (`A2:9B:97:3D:38:5E`) — чужой трафик в том же логе.

## 6. Что писать в форк дальше (не в этой сессии)

Когда C PASS на ванили:

1. Зафиксировать три тактики в коде как явные пути (не «default combo на всё»).
2. Дать monitor три сигнала: QUIC googlevideo жив / youtubei 405 / TCP ECH seek (ретраи `0x16` без `0x17` за N секунд).
3. ABD на YouTube переключает только A/B/C и откат на nosplit/rexmit.
4. PPE — отдельный слой после L4 pcap, окно handshake, не маскировка.
5. uTLS не нужен в NFQUEUE; если понадобится — только исходящие dials самого b4 (DoH/discovery).

Пока C не PASS на ванили — не крутить split. LIVE откат **nosplit**. ПК `.40` — отдельный клиент (ниже).

### Итоги сессии 22.08 (L-steer v1 FAIL → карта закрытых путей и экономика QUIC)

**Эксперимент `b4.exp-steer` `69b18178`:** RST по детекту ECH в записи в воронке `dropAndInjectHandshake`, youtube-video only, глушение повторов потока 10 c по tuple. Тест владельца 08:46–47 UTC: ваниль — тормоза при ЗАГРУЗКЕ и seek; ReVanced — одно зависание. Откат holdch3 08:54 UTC. Механика при этом точна: 10× steer ровно на doomed-классе (`.152`→74.125.162.71, ech=1, CH 1743–1839 B), ни одного вне youtube-video, QUIC жив весь тест.

**Главный факт (Cronet-профиль):** быстрый RST НЕ уводит Cronet на QUIC — он штормит новыми TCP: свежие source-порты каждые 3–13 c ≥30 c подряд, по ДВА соединения ~100 мс на попытку (46960/46962→41896/41912→41926/41944→40428/40442→44068/44080); каждый цикл SYN→SYN-ACK→CH→hold(~80 мс)→RST. Chromium трактует RST как transient-ошибку и ретраит агрессивно. Подавление по tuple новые порты не ловит BY DESIGN. Следствие для любых будущих RST/steer механизмов: гасить SYNs **клиент-scoped** (clientMAC+dstIP), иначе механизм сам создаёт тормоза.

**v2 (проведена 22.08, `fc8b08ed`):** после первого steer пары (clientMAC+dstIP) SYNs к этому IP дропались молча ~10 c. Механика точна (110 армингов, 723 dropped SYN, гвардии без промахов), UX **FAIL**: ваниль виснет при перемотке, ReVanced часть роликов с большой задержкой. Причина: молчаливый SYN-drop ядро считает потерями — экспоненциальный backoff тех же tuple, connect() в limbo дольше, чем при holdch3. Риск «трогает весь gv-TCP клиента» материализовался. Steer-семейство закрыто целиком (см. таблицу выше).

**Автоматизация гейта механики:** телефонный CH синтезируется — `fixtures.BuildTLSClientHello(host, 0x0304, ech=true, targetSize≈1800)` + нарезка 1396+хвост сырым сокетом с ПК. Автопроверяемо: классификация сета, маркер `[steer]` в логе, время до RST, гашение ретраев, анти-ущерб (чистый CH без ECH не должен steered/dropped; QUIC не трогается). curl.exe непригоден как зонд ([00]-порча CH). Финальный UX-вердикт остаётся ручным (.152) — правило не меняется.

**Криптографические закрытия (обсуждено с владельцем 22.08; это свойства TLS 1.3 / RFC 8446, а не запреты — не переоткрывать):**

| Идея | Почему невозможно |
|---|---|
| Вырезать/править ECH-ext in-flight | транскрипт TLS 1.3: клиент хэширует СВОИ байты CH, сервер — ПОЛУЧЕННЫЕ; расхождение → Finished клиента не верифицируется = `SEC_E_DECRYPT_FAILURE`. Это и есть механизм провала b4x-smo (T8). PSK-binders отвергают изменённый CH ещё раньше |

Вывод: стена привязана к содержимому, которое нельзя менять ⇒ закрыты ВСЕ содержимые классы разом (mutation, strip, replay, подстановка). Остаются путевые: steering на маскируемый QUIC, здоровье QUIC-пути, туннельный класс (addenda WARP, P1+).

**Экономика QUIC (для будущего монитора):** криптографии против резки QUIC у ТСПУ нет — ключи Initial выводятся из открытого DCID, SNI читаем. Держат их только: цена (AEAD на линейной скорости + состояние UDP/CID-миграций против дешёвого TCP стринг-матча), collateral (по UDP/443 идёт HTTP/3 всего веба, звонки, игры), политэкономия полного блока YouTube. Дешёвая альтернатива у них существует: тупой лимит/дроп UDP/443 по диапазонам без расшифровки. Деградация будет ПЛАВНОЙ (столлы, не чистая резка) → сигнал монитора: «fake UDP ушёл, данных нет». Живость QUIC — эмпирика текущего дня, не гарантия протокола.
