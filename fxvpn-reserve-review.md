# E-FXVPN: ревью реализации резервного туннеля Firefox VPN (v1, 2026-09-02)

Статус: ревью кода ветки `agent/classifier-v2.3-capture-envelope` (HEAD 87ef91a) против
дизайна `fxvpn-reserve-design.md` (v1+v2, 2026-08-25). Объект ревью: `src/transport/fxvpn`
(FX1–FX3), `src/fxvpservice` (FX4-сборка), `src/http/handler/fxvpn.go`,
`src/observability/fxvpn.go`, `src/config/fxvpn.go`, интеграция в демон.

Формат: вердикт и карта покрытия → находки по убыванию серьёзности → рекомендации →
**отдельная глава «Маскировка» (§7)** — дизайн противодействия ТСПУ по аналогии с
awg-warp/awg-proton, подготовленный для реализации агентом.

---

## 1. Вердикт

FX1/FX2/FX3-слои — самый функционально полный из трёх резервов: контрольная плоскость FxA
(PBKDF2/HKDF authPW, Hawk, OAuth, refresh с сохранением старого refresh-токена),
Guardian-клиент с квота-заголовками и Retry-After, Fastly PoW/PAT-солвер с exit-IP-привязкой
куки, serverlist-кэш с ETag/304, самописный H3-стек поверх quic-go, H2-CONNECT с
ring-buffer'ом вместо io.Pipe (правильный throughput-фикс), account pool с
reset-aware recycling, HTTP API на 5 эндпоинтов, observability-модуль. События и классы
отказов соответствуют таксономии дизайна.

Но в живом пути есть **три критических дефекта**: H2-туннель обрывается по дедлайну
установки (контекст запроса не отсоединяется после 2xx — долгоживущие релеи умирают через
20 секунд), H3-носитель не умеет резолвить имена узлов (а список даёт только имена), и
преэмптивная ротация пула — ключевая фича v2-дизайна — математически недостижима, пока
сессия жива. Плюс главный интеграционный пробел, общий с Opera: рантайм не собирается и не
стартует в main.go — handler'ы всегда отвечают disabled-шейпом.

| Область | Оценка |
|---|---|
| Контрольная плоскость FX1 | Хорошо; TOFU-пин слабее оперы (коммит до доказательства) |
| Дата-плоскость FX2 | H2 — критичный баг времени жизни; H3 — нерабочий для хостнеймов |
| Аккаунт-пул FX3 | Логика верная; преэмптивная ротация не вызывается в живом пути |
| Интеграция FX4 | Handler+observability есть; **main-wiring и потребители DialStream отсутствуют** |
| Маскировка | Отсутствует (дизайн её и не предусматривал — закрыто главой 7) |

## 2. Что реализовано (карта)

- `fxa.go` — вывод authPW (PBKDF2-SHA256 1000 → HKDF, stdlib Go 1.24+), Hawk-заголовки
  (deriveHawkCredentials/hawkHeader с payload-hash), логин с email-2fa + errno-107
  фолбэк, VerifySession, OAuth fxa-credentials, RefreshToken с сохранением старого RT.
- `guardian.go` — fpn/token|status|activate, JWT-клеймы без подписи (пин вместо неё),
  X-Quota-*, Retry-After (delta-seconds и HTTP-date), детект сдвига часов сервера
  (guardian.go:262 — сетка таймзон/15-мин — хороший перенос референса).
- `fastly.go` — солвер challenge: 406-детект, страница/script.js, init-парсер, PoW
  62² перебор, PAT-фолбэк на пустом auth, clientmetrics-заглушка, post-back ≤3 раунда,
  проба куки перед установкой (exit-IP-ротация), сериализация солвера per-ControlPlane
  (chMu), minBudgetContext (не даёт коротким таймаутам убить mid-solve).
- `controlplane.go` — один HTTP-клиент+jar (кука привязана к exit — архитектурно верно),
  dialTLS с TOFU-пином поверх стандартной верификации цепочки, SetBaseDial/SetTransport
  (швы bootstrap-through-carrier).
- `serverlist.go` — Remote Settings, парсинг обеих форм записей (bare → connect),
  quarantine-исключения, ETag/304, stale-fallback при сетевой ошибке, персист.
- `h2tunnel.go` — ALPN h2, keepalive PING 10с/бюджет 15с, UpdateToken in place,
  tunnelWriteBuffer (ring buffer) — throughput-фикс референса, CloseWrite-полузакрытие.
- `h3tunnel.go` — QUIC ALPN h3, InitialPacketSize 1200 (правильный low-MTU урок),
  классификация отказов хендшейка (udp-egress-blocked / h3-negotiation-failed),
  ручной CONNECT + DATA-фреймы, очистка дедлайна после установления (в отличие от H2!).
- `pool.go` — состояния жизненного цикла, порог ротации 15%, reset-lead 24ч,
  cooling_down анти-флап, бэкофф refresh, ban после 3 strikes, RecycleDue,
  MarkExhausted/MarkAuthRejected (события с ред-аккаунтов).
- `ladder.go` — H3→H2 с одним подтверждённым свитчем и cooldown 300с, анти-осцилляция.
- `exitprobe.go` — Cloudflare trace через туннель, ExitMismatchError → класс.
- `fxvpservice` — restartGuard (≤6/ч + cooldown), тик 30с, DialStream, статус
  running/listening, Locations/ValidateLocation/SetLocation, TestAccount (без открытия
  туннеля — правильное разделение), BypassSuffixes (антипетля).
- `http/handler/fxvpn.go` — 5 эндпоинтов со swagger-аннотациями, регистрация в
  common.go:207. `observability/fxvpn.go` — метрики пула/диалов.

## 3. Находки

### CRITICAL

**F1. H2-туннели живут не дольше OpenBudget (20 с).**
`OpenTunnel` (h2tunnel.go:139): `octx, cancel := context.WithTimeout(parent,
s.cfg.OpenBudget)` — и этот контекст становится контекстом ЗАПРОСА
(`http.NewRequestWithContext(octx, …)`). После `cc.RoundTrip` и 2xx стрим остаётся
привязанным к req-context: x/net/http2 при срабатывании Deadline посылает RST_STREAM и
закрывает resp.Body. `tunnelConn` хранит только `cancel` (досрочная отмена), но дедлайн
в 20 секунд ничем не сбрасывается — http2 не позволяет «отсоединить» контекст.
**Следствие: каждый долгоживущий CONNECT-релей умирает через ~20 секунд после
установления** — стримы telnet/ssh/загрузки оборвутся. Тесты этого не ловят: фейковые
эджи обмениваются данными доли секунды.
Асимметрия-подсказка: H3-путь ЯВНО чистит дедлайн
(`stream.SetDeadline(time.Time{})` с комментарием «must not kill the long-lived relay») —
для H2 аналогичная забота не сделана.
Фикс: разделить «бюджет установления» и «время жизни»: создать req на
`context.WithCancel(parent)`, а таймаут завести вручную (`time.AfterFunc(OpenBudget)`) и
остановить его (`t.Stop()`) при получении 2xx; cancel остаётся в tunnelConn для Close.
Плюс регресс-тест: туннель, живущий > OpenBudget с exchange посередине (фейк-эдж с
delayed-write).

**F2. H3-носитель не умеет DNS-имена — prefer_h3=true нерабочий в проде.**
`DialH3` (h3tunnel.go:74): `quic.Dial(dctx, uc, &net.UDPAddr{IP: net.ParseIP(cfg.Host),
Port: cfg.Port}, …)`. `net.ParseIP("atn1.m1.fastly-masque.net")` = nil →
`UDPAddr{IP:nil}` → диал в никуда/ошибка. `resolveLocation` возвращает **имена** из
serverlist (прод-записи — hostname:2499), H2 при этом резолвит сам (tls.DialWithDialer),
H3 — нет. Тесты проходят, потому что фейк-эджи слушают на 127.0.0.1.
Фикс: резолвить cfg.Host до quic.Dial (через `net.Resolver` или, лучше, через
существующий `transport/dns`-менеджер с DoH-гонкой — он уже в программе), SNI/ServerName
оставить именем. Резолв кладётся рядом с `cfg.Policy.ListenUDP`, результат — в
`net.UDPAddr`. Плюс: семейство udp/udp6 вычислять после резолва (сейчас — по ParseIP, для
имён всегда «udp» — на dual-stack может дать IPv6-сокет под IPv4-цель или наоборот).

**F3. Преэмптивная ротация пула недостижима при живой сессии.**
`ensureSession` (fxvpservice/service.go:306): если сессия `IsAlive` — немедленный return.
`RotateIfDue` вызывается ТОЛЬКО из ensureSession — т.е. только когда сессия мертва.
Триггер A («остаток <15% → прогрев следующего и атомарный свап ДО исчерпания») и триггер B
(reset-lead) **никогда не проверяются, пока сессия жива** — ровно в тот период, ради
которого они спроектированы. Ротация происходит пост-фактум: аккаунт доедает квоту в
mid-traffic, сессия умирает, лишь затем DialStream/тик запускают свап. Контракт
«pre-emptive» из v2-дизайна (наше заявленное усиление против референса) — мёртвый код в
живом пути (юнит-тесты зовут RotateIfDue напрямую, поэтому зелёные).
Фикс: в `tick()` вызывать `pool.RotateIfDue(ctx)` до `ensureSession` безусловно; при
свапе живой сессии — не закрывать старую немедленно (существующие стримы доживают,
`swapTo` уже так задуман), только перевыпустить bearer и пересобрать сессию при следующем
естественном цикле (или soft-swap: старая сессия продолжает обслуживать открытые стримы,
новые диалы идут в новую).

**F4. Рантайм не подключён к демону.**
`main.go` не содержит fxvpn-блока: `fxvpservice.Build/Start` не вызываются,
`handler.SetFxvpnRuntime` не вызывается никогда (grep: только определение). Все 5
эндпоинтов `/api/fxvpn/*` отвечают disabled-шейп даже при `system.fxvpn.enabled=true`.
`DialStream` не имеет потребителей (scoped-маршрутизатор/деревья выбора не знают kind
fxvpn). Канон для фикса — блок proton в main.go:636–655.

### HIGH

**F5. TOFU-пин коммитится до доказательства канала.**
`PinStore.Verify` (pin.go:63): неизвестный хост → немедленная запись+персист пина
**сразу после завершения TLS-рукопожатия**, до какого-либо HTTP-обмена. MITM на первом
контакте (классическая слабость TOFU) закрепляется навсегда. У Opera и Proton сделано
сильнее: pending → commit только после успешного обменa (Opera: «parseable SurfEasy reply
proves the pending fingerprint genuine»; Proton: Commit после успешного ответа API).
У Mozilla-хостов стабильные публичные сертификаты — двойная защита возможна.
Фикс (двухслойный): (а) pending→commit после первого 2xx/parseable ответа через канал
(перенести логику opera/pin.go); (б) seed-пины трёх хостов (api.accounts.firefox.com,
vpn.mozilla.org, firefox.settings.services.mozilla.com) из полевого сертификата —
владелец снимает SPKI SHA-256, мы храним как seed (аналог 10 seed-пинов Proton);
расхождение seed+нет-пина → явное событие, авто-TOFU только при недоступности seed.

**F6. Антипетля-гвард DialStream мёртв для прод-трафика.**
`DialStream` получает `netip.AddrPort` — `addr.Addr().String()` это **IP**. Далее
`IsBypassDomain(host)` сравнивает IP с доменными суффиксами — всегда false;
`strings.EqualFold(host, nodeHost)` сравнивает IP с именем узла (sessionHost — hostname) —
всегда false. `ErrFxvpnSelfLoop` недостижим. Реальная защита должна жить ДО резолва — на
стороне scoped-роутера/DNS (BypassSuffixes экспортированы — хорошо), но заявленный в
комментарии in-code гвард не работает.
Фикс: проходить в DialStream пару (host, resolvedIP) (контракт warp-StreamDialer
расширить или проверять на уровне маршрутизатора), либо резолвить nodeHost и сверять IP
(кэш IP узла на время сессии), либо отказаться от in-code гварда с честным комментарием.

### MEDIUM

**F7. Квота-телеметрия не обновляется (нет 15-мин поллинга и счётчика байт).**
Дизайн Ч.I §3: «локальный счётчик байт сессии + поллинг X-Quota-Remaining каждые 15 мин».
Реализовано: значения квоты обновляются только при перевыпуске pass (`RenewActivePassIfNeeded`
— за 2 мин до exp, а JWT живёт долго) и при варме аккаунта. Прогресс-бар GUI показывает
числа, которым часы; локальный счётчик байт отсутствует вовсе (dialOK/dialFail не в счёт).
Фикс: (а) в tick — при живой сессии раз в 15 мин `FetchProxyPass` (дёшево, обновляет
квоту+перевыпускает pass раньше срока — двойная польза) или отдельный лёгкий вызов;
(б) байт-счётчик: обернуть tunnelConn.Read/Write атомарными счётчиками, экспортировать в
Status/метрики (observability уже есть — добавить gauge `fxvpn_bytes_total{dir}`).

**F8. `resolveLocation` всегда берёт `cands[0]` — узел не ротируется при деградации.**
Дизайн II.2.4: RTT-ранжирование + durability-burst + «замена при 3 подряд неудачах узла».
Реализовано: первый кандидат всегда; сбойный первый узел = все диалы падают до
срабатывания session-health трекера (3 РАЗНЫХ цели) или смерти сессии. RTT/страйков нет.
Фикс: (а) страйки per-node (канон `twg.StrikeState`, уже используется proton-сервисом):
N=2 подряд неудач узла → следующий кандидат (cands[i+1 mod n]); (б) при построении
кандидатов — лёгкое RTT-ранжирование (TCP-диал-проба, паттерн discovery WARP).

**F9. `verifyExit` любую ошибку пробы считает exit-mismatch.**
`verifyExit` (service.go:411): при ошибке пробы (в т.ч. туннельной) → `noteFailure(
fxvpn.ClassExitMismatch)` + событие `fxvpn_exit_probe_failed`. Класс mismatch не
зарезервирован за гео-несоответствием: трека «probe failed» портит статистику реальных
mismatch'ей. Мелкая косметика телеметрии.

**F10. SetLocation расходует рестарт-бюджет.**
`SetLocation` закрывает сессию; следующий ensureSession делает `guard.stamp()` — смена
локации 7 раз в час упрётся в кап, и смена будет «не работает» без объяснений. Фикс:
различать административный rebuild (SetLocation/RestartNow с явного действия) от
автоматического (как минимум — событие при отказе из-за капа).

### LOW

**L1. `Locations().FetchedAt` никогда не заполняется** (service.go:572-577: блок с
комментарием «filled below from cache snapshot» присваивает zero-time и всё). Фикс:
отдать `sc.cur.FetchedAt` через геттер кэша.

**L2. `pool.refreshFailed` шлёт EvPoolBlocked на бан одиночного аккаунта** — семантически
это аккаунт-левел событие (забрать событие `fxvpn_account_banned`), pool_blocked
зарезервирован за «нет ни одного обслуживаемого». Текущий вызов из `fetchPass` «entitlement
refused» — тоже.

**L3. `warmCandidate`: мёртвый `_ = rtState`** (pool.go:413) — следы рефакторинга.

**L4. `markExhausted` вызывается из fetchPass под `p.mu.Lock()`, а в MarkExhausted —
локается дважды?** Нет — korrekt: внутренний вариант без лока, оба вызова корректны; но
комментарий «this variant locks itself» вводит в заблуждение (наоборот — НЕ лочится).
Косметика.

**L5. `tunnelWriteBuffer.Read` отдаёт short read при wrap кольца** — допустимо по
контракту io.Reader, но http2-транспорт в редких версиях не любит short reads в request
body; поведение стоит зафиксировать тестом (есть в fakeh2edge-матрице? — добавить).

**L6. `clientMetricsAnswer` фейковый детект-фрейм** — честно задокументирован
(«текущий конфиг Mozilla выдаёт только PAT/PoW»); при смене конфига Fastly капча станет
структурным отказом — класс `fxvpn-challenge-failed` уже есть. ОК.

**L7. Hawk nonce 6 байт/секундный ts — совпадает с референсом; угроза replay-окна
секундная — приемлемо для этой threat-модели.

**L8. `parseQuotaInt` парсит float → int64 усечением** — для X-Quota-* в байтах ок.

## 4. Что сделано лучше дизайна/референсов (сохранить)

1. `tunnelWriteBuffer` (ring buffer вместо io.Pipe) — правильный перенос throughput-фикса
   референса; CloseWrite-семантика продумана (буфер дочитывается после half-close).
2. `minBudgetContext` — аккуратная защита mid-solve флоу от коротких внешних дедлайнов
   (watcher-goroutine с корректным стопом).
3. Лестница H3→H2 с однократным свитчем/кулдауном — канон EH3 переиспользован честно.
4. `failureTracker` — точный перенос эвристики «3 разных цели».
5. Serverlist: stale-fallback и обработка bare-записей — соответствует живому списку.
6. TestAccount — чистое разделение «проверка кредов без поднятия туннеля».

# 7. ГЛАВА: МАСКИРОВКА FIREFOX VPN ОТ ТСПУ (дизайн для реализации)

Цель — чтобы ТСПУ не смог (а) отличить fxvpn-трафик от легитимного браузерного
Firefox/Mozilla-трафика, (б) построить устойчивую сигнатуру для целевой глушилки. Строим
по аналогии с awg-warp/awg-proton: контролируемый первый пакет, правдоподобный отпечаток,
лестница с last-good, честные нерешаемые ограничения. Важный контекст: **контрольная
плоскость fxvpn уже частично замаскирована сама по себе** (UA MozillaVPN, Fastly-анти-бот
даже помогает: кука = proof-of-work), поэтому глава сфокусирована на дата-плейне и на
объёмных сигнатурах.

## 7.1. Что видит ТСПУ сегодня (инвентаризация сигнатур)

Дата-плейн «connect»-диалекта:

| Сигнатура | Сегодня | Видимость |
|---|---|---|
|Dst-порт **2499** (единый для всего списка) | фиксируется сервером | **Высокая — главный вектор атаки ТСПУ**: редкий порт, постоянный для фичи |
|Dst-IP: `*.m1.fastly-masque.net` (Fastly-диапазоны, известно как infra Mozilla VPN) | фиксируется | Высокая |
| QUIC-путь (prefer_h3): Initial к :2499 с ALPN h3, hello = Go-crypto/tls-отпечаток | SNI=имя узла (ok), но JA4≠Firefox | Высокая (для QUIC-классификатора) |
| TLS-путь (H2): TLS1.3 к :2499, ALPN h2, Go-отпечаток, SNI=имя узла | JA3/JA4 Go | Высокая |
| Соединение после CONNECT | долгоживущий байтовый поток (та же картина, что у оперы) | Средняя |
| Контрольная плоскость | UA MozillaVPN/2.35.0, обычный TLS к Mozilla-хостам | Низкая (легитимный профиль; PoW-кука даже повышает правдоподобие) |

Ключевой вывод: в отличие от Opera, у fxvpn SNI и имена уже легитимные (host узла —
настоящий Fastly-хост), а главные сигнатуры — **порт 2499 и отпечаток ClientHello**.
Порт неустраним на уровне провода (сервер слушает только его) — поэтому центральная
идея главы: **порт и IP блокируются последней эскалацией, а до неё — делать поток
неотличимым; когда блокируют порт — уходить в носитель (вложение)**.

## 7.2. Принцип переноса amnezia-семантики

| Amnezia (UDP/WG) | FXVPN — проект |
|---|---|
| I1-приманка перед хендшейком | **QUIC pre-flight fake с малым TTL** (7.4.1) — UDP не ретрансмится, фейк доходит до ТСПУ и умирает до сервера; для TCP-ветки — NFQ fakedsplit как у оперы (7.4.2) |
| Jc-мусор | Не нужен: Initial и так насыщен |
| Стандартный хендшейк | Отпечаток hello под Firefox (7.4.3) |
| VanillaSafe-инвариант | Пин/WebPKI не ослабляется (7.4.0) |
| Лестница профилей | Лестница носителей 7.5 (H3-native → H3+fake → H2 → H2-in-carrier) |
| SNI-пул + ротация | SNI уже валиден (имя узла) — не трогаем; добавляем только ротацию выбора узла |

## 7.3. Конфигурационная модель (для реализации)

```
system.fxvpn.masquerade {
  profile: "firefox"     // firefox | go-plain | off
  preflight_fake: true   // QUIC TTL-приманка (7.4.1)
  hello_shaping: true    // Firefox-отпечаток QUIC/TLS (7.4.3)
  initial_padding: 1250  // размер Initial как у Firefox (7.4.3)
  nest_on_port_block: true // авто-вложение в carrier при блоке порта (7.5)
}
```

## 7.4. Механизмы

### 7.4.0. Инвариант
Маскировка не ослабляет аутентификацию: для QUIC-пути quic-go верифицирует цепочку
(сервер = настоящий Fastly) — приманки идут ДО Initial и не участвуют в TLS; для
H2-пути пин-контроль остаётся штатным. Fake-датаграммы никогда не подменяют
настоящий Initial, только предшествуют ему.

### 7.4.1. QUIC pre-flight приманка с TTL («I1 для H3-носителя») — главный механизм
UDP позволяет то, что невозможно на TCP: **фейковую датаграмму, которая доходит до DPI и
умирает до сервера, без ретрансмиссии**. Схема (реализация ~80 строк):

1. После `ListenUDP` (уже есть) и ДО `quic.Dial`: выставить
   `udpConn.SetTTL(ttlFake)` (Go поддерживает `net.UDPConn.SetTTL` с Go 1.23? — если нет,
   через `Control`+`IP_TTL` на сыртом сокете через `ListenConfig.Control` — паттерн
   `SO_MARK` из `transport/wg/socket_linux.go` переносится 1:1);
2. отправить 1–2 фейковых Initial-ПОДОБНЫХ датаграммы: полный QUIC long-header
   (0xC0…, v1, случайный DCID 8Б) с **SNI из белого пула** — использовать
   существующий генератор `proton.BuildQuicInitial` (пакет transport/proton уже умеет
   строить настоящие Initial'ы — реюз без новой зависимости! Вариант: вынести генератор
   в общий internal-пакет, чтобы не создавать обратную зависимость);
3. `SetTTL(default)` восстановить, далее настоящий `quic.Dial`.
DPI на транзите видит: QUIC-Initial с белым SNI → умирает → настоящий Initial с SNI
fastly-узла. Классификатор, обученный на «первом Initial потока», прочитает белый SNI.
Параметры: `ttl_fake` = 2–4 (поле калибрует: TTL должен покрыть хопы до DPI, но не до
Fastly — типично 8+); количество фейков 1–2 со случайным интервалом 0–50мс.
Риск: Fastly-сервер НЕ видит фейк — совместимость полная (в отличие от amnezia, где
мусор доходит до пира и им отбрасывается). Дополнительный бонус — фейк-датаграммы
создают UDP-«шум» перед потоком, ломая per-flow статистику первого пакета.

### 7.4.2. TCP-ветка (H2): приманка через штатный NFQ (совместно с оперой)
H2-путь — TCP, TTL-трюк из 7.4.1 на живом сокете портит поток (ретрансмиссии). Решение
то же, что предложено для Opera в opera-reserve-review §7.4.3: `SO_MARK =
packetmark.MarkFxvpnEgress` на сокетах H2-сессии → OUTPUT-mangle → NFQUEUE →
существующий action-планировщик применяет **fakedsplit/fakeddisorder** с фейковым
ClientHello из `tlsgen.GenerateTLSClientHello` (белый SNI первым расширением —
специализация tlsgen против ТСПУ). Инфраструктура единая для обоих резервов —
реализуется один раз (см. opera-ревью, этап OP-M3; здесь этап FX-M3).

### 7.4.3. Отпечаток под Firefox
- **QUIC (H3)**: quic-go собирает ClientHello через crypto/tls → Go-отпечаток. Firefox
  использует свой набор (chacha20+gcm, X25519, ALPN h3, специфичный порядок
  расширений + GREASE). Полный мимикри-путь — uTLS-интеграция с quic-go
  (quic.Config{TLSConfig} принимает crypto/tls; для uTLS нужен форк с
  tls.ClientHandshake shim — существует в сообществе). Красная линия «ноль новых
  зависимостей» → решение владельца (прецедент amneziawg-go v3). Промежуточный
  дешёвый слой (обязательно): CurvePreferences/ CipherSuites порядок под Firefox,
  `InitialPacketSize`→padding до 1250 (Firefox паддит Initial до ~1200-1250 — сейчас
  у нас 1200 ровно, что тоже маркер), датаграмма pmtud-размеров.
- **TLS (H2)**: те же Curve/suites; полный профиль — uTLS `HelloFirefox_Auto` (тот же
  вендоринг, одна зависимость на оба пути).
- **Данные/стримы**: QUIC-фреймы уже неотличимы (стандартный h3-стек); ничего не нужно.

### 7.4.4. Поведенческий слой
- Одновременность носителей: H3-диал без предварительного TCP-проба (сейчас лестница
  ошибок создаёт «TCP-проба → QUIC» последовательность — терпимо; не усиливать).
- Keepalive PING 10с (H2) / 30с (H3) — Firefox-подобные; ок.
- Сокращение числа хендшейков: сейчас сессия ОДНА долгоживущая — уже хорошо; после
  фикса F1 не появится « reconnect-шторм», который был бы сигнатурой.

### 7.4.5. Контрольная плоскость — не трогать
UA MozillaVPN + PoW-кука + нормальный WebPKI-TLS к публичным хостам Mozilla =
максимально легитимный профиль из возможных. Единственное улучшение: тот же
hello-shaping (7.4.3) для `ControlPlane` — опционально, после вендоринга uTLS.

## 7.5. Лестница носителей + авто-эскалация при блоке порта

Порт 2499 — приоритетная цель ТСПУ (дешёвое правило: `dst port 2499 and dst asn=fastly`).
Ответ многоступенчатый:

```
[ H3-native: QUIC→:2499, Firefox-hello, preflight-fake ]   # маскировка полная
  → [ H2: TLS→:2499, Firefox-hello, NFQ-fakedsplit ]        # если QUIC глохнет (существующая лестница)
  → [ H2/H3 ВЛОЖЕННЫЙ в carrier ]                           # блок порта/IP: дата-плейн через базовый туннель
  → [ остановка транспорта, honest-fail ]                   # блокируется всё
```

Вложение — центральная эскалация: **fxvpn-сессия внутри активного WARP/MASQUE-туннеля**.
Механика уже существует в программе: `transport/nested/masque_carrier.go`,
`transport/nested/wgmasque.go` (WG-внутри-MASQUE) — тот же паттерн
«ControlPlane.SetBaseDial» уже несёт контрольную плоскость через carrier; расширение —
пропустить через carrier и **UDP/TCP-ногу дата-плейна**: для H2 — SetBaseDial на
TunnelConfig-диалер (шов есть: `TunnelConfig.Policy.Dialer()`... добавить
`Policy.BaseDial`); для H3 — UDP-диал через carrier требует UDP-эгресса у носителя
(MASQUE CONNECT-UDP есть в nested/udpdgram.go — готово!). DPI видит только
обфусцированный поток базового туннеля; Fastly видит exit-IP базового туннеля —
совместимость с «кука привязана к exit IP» сохраняется (весь fxvpn живёт на одном
exit'е).
Триггер эскалации: детектор блокировки (существующий `src/detector`): N подряд
QUIC-хендшейк-таймаутов ИЛИ TCP-сбросы на :2499 при живом прочем трафике → событие
`fxvpn_port_block_suspected` → авто-включение вложения (`nest_on_port_block`) с
кулдауном и last-good (возврат наверх раз в час пробой, анти-осцилляция канон
`ladder.go`).

## 7.6. Ограничения (зафиксировать честно)

1. **Порт/IP Fastly** блокируются правилом, а не сигнатурой — лечится только вложением
   (7.5) или сменой вендора (это роль Opera/Proton — ортогональность резервов).
2. Fastly-anti-bot может ужесточиться (капча вместо PoW) — класс
   `fxvpn-challenge-failed` уже есть; авто-солвер капчи вне принципов программы.
3. Аккаунт-модель (реальные FxA) — блокировка аккаунтов Mozilla не лечится маскировкой;
   роль пула.
4. UDP-эгресс (masque-диалект) — будущая ветка; маскировка разрабатывается под
   connect-диалект (текущий прод).

## 7.8. Красные линии главы

1. Приманки никогда не подменяют настоящий handshake и не ослабляют верификацию
   (WebPKI/пины) — только предшествуют.
2. TTL-фейк только на UDP-пути (QUIC); на TCP — только NFQ-механика (7.4.2), никаких
   «TTL-трюков на живом сокете».
3. Вложение в carrier не включается молча — событие + кулдаун + честный статус
   («fxvpn nested in warp-carrier»).
4. uTLS — решение владельца, обновление NOTICE.
5. Контрольная плоскость Mozilla/Fastly не получает НИ ОДНОГО запроса сверх описанных
   потоков (канон красной линии 10 Ч.II).
