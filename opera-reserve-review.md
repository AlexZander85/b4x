# E-OPERA: ревью реализации резервного туннеля Opera/SurfEasy (v1, 2026-09-02)

Статус: ревью кода ветки `agent/classifier-v2.3-capture-envelope` (HEAD 87ef91a) против дизайна
`opera-reserve-design.md` (v1, 2026-08-24). Объект ревью: `src/transport/opera` (OP1–OP3),
`src/operaservice` (OP4-сборка), `src/config/opera.go`, интеграция в демон.

Формат: сначала вердикт и карта покрытия, затем находки по убыванию серьёзности
(CRITICAL → HIGH → MEDIUM → LOW), затем рекомендации, затем **отдельная глава «Маскировка»**
(§7) — дизайн противодействия ТСПУ по аналогии с awg-warp/awg-proton, подготовленный для
реализации агентом.

---

## 1. Вердикт

Ядро (Digest-аутентификация, TOFU-пиннинг API, identity-слот, TLS+CONNECT дата-плейн,
health-супервизор с ротацией и капами) реализовано **качественно и ближе к дизайну, чем у
референсов**: закрыта дыра InsecureSkipVerify всего семейства (§3 дизайна), digest написан
компактно и заперт golden-тестами, identity персистится атомарно с карантином. Код читается,
инварианты задокументированы в комментариях с указанием file:line референсов.

Однако туннель **не доведён до роли транспорта в программе**: нет wiring в main.go, нет HTTP
API (у fxvpn/proton есть), нет observability-модуля, `Runtime.DialStream` не имеет
потребителей — движок не может направить в Opera ни один scope. Плюс два эксплуатационных
дефекта: супервизор может зависнуть на неограниченной по времени пробе, держа мьютекс (блокируя
Status()), а верификация узлов опирается на системное хранилище корней, которого на роутере
может не быть — против явно заданного дизайном встроенного Mozilla/NSS-пула.

| Область | Оценка |
|---|---|
| Контрольный канал (OP1) | Хорошо; bootstrap-стек дизайна §2 реализован на ~20% (только carrier-failover) |
| Дата-плейн (OP2) | Хорошо; системный root-pool — отклонение от дизайна |
| Здоровье (OP3) | Хорошо в логике; риск wedged-тика — CRITICAL |
| Интеграция (OP4) | **Не завершена**: main/handler/router/observability отсутствуют |

## 2. Что реализовано (карта)

- `seclient.go` — SurfEasy API: register_subscriber → register_device, subscriber_login +
  device_generate_password (4ч-ротация JWT), geo_list, discover с регионом; заголовки
  маскировки под браузер; гонка форм отсутствует (всё через один `rpc`); нc-дисциплина digest
  корректна (мьютекс клиента сериализует).
- `digest.go` — минимальный RFC 7616 профиль (MD5, qop=auth, cnonce из crypto/rand,
  монотонный nc per-nonce, stale=true ретрай, отказ классифицируется). Парсер
  WWW-Authenticate честный (квоты, escape), валидация алгоритма → `ClassAPIAlgorithm`.
- `pin.go` — TOFU SPKI: pending → commit **после** успешного декода ответа API (сильнее, чем
  у fxvpn: доверие только доказавшему каналу), расхождение = `opera-api-pin-mismatch`,
  fail-closed.
- `identity.go` — слот 0600 tmp+fsync+rename, карантин `*.corrupt`, Validate перепроверяет
  SHA1-деривацию device-hash, Redacted() вычищает всё секретное.
- `dataplane.go` — TLS (SNI подавлен/fake) + ручная VerifyConnection против реального имени
  узла, HTTP/1.1 CONNECT с Basic-авторизацией, prefixConn-переигрывание буфера (важная деталь
  референса), Relay с семантикой «чистый EOF = успех».
- `health.go` — состояния running/listening раздельно; двухуровневая проба (дёшево/дорого);
  ротация кэша без пересоздания сессии; EU→AM-фолбэк + экспоненциальный возврат к желаемому
  региону (Nova-паттерн); кап рестартов ≤6/ч + cooldown 300с; JWT-обновление по каденции 4ч.
- `operaservice/service.go` — сборка, антипетля (SecTunnelBypassSuffixes + отказ
  self-loop по IP узла), UDP fail-closed, carrier-failover (direct → базовый туннель).
- `config/opera.go` + `config/validation.go:385` — валидация региона/ControlTarget даже в
  выключенном состоянии (канон программы).

## 3. Находки

### CRITICAL

**C1. Интеграция в демон отсутствует — транспорт «мёртвый код».**
В `main.go` нет блока оперы (grep: только proton wired, строки 636–655). Нет
`SetOperaRuntime`, нет `http/handler/opera.go` — у fxvpn и proton HTTP API есть
(`/api/fxvpn/*`, `/api/proton/*`), у оперы нет ни `/api/opera/status`, ни смены региона, ни
restart. `Runtime.DialStream` (Backend-B контракт) не потребляется ни scoped-маршрутизатором,
ни деревьями выбора — ни одного вызова вне тестов. Ключевая фича дизайна §5 («bootstrap-API
звонится ЧЕРЕЗ наш работающий базовый транспорт») частично есть (failoverDialer), но роли
`kind: opera` в движке не существует. **Следствие: включение `system.opera.enabled=true` в
прошивке ничего не изменит** — движок не соберётся и не стартует. Красная линия «валидировать
и в выключенном состоянии» соблюдена, но включаемого состояния не существует.
Фикс: блок в main.go по канону proton (if-gate по `cfg.System.Opera.Enabled` →
`operaservice.Build(cfg, Options{Carrier: …})` → Start → `handler.SetOperaRuntime`),
`RegisterOperaApi()` (status/region/restart) и регистрация носителя в деревьях выбора ниже
WARP/MASQUE/H3.

**C2. HealthSupervisor может зависнуть навсегда, заблокировав Status().**
`Tick()` (health.go:280) выполняет сетевые пробы, **удерживая `h.mu`**, и передаёт в пробу
`h.ctx = context.Background()` (health.go:252) — **без дедлайна**. В `NodeDialer.dialNodeTLS`
TCP-диал ограничен 15с, но `HandshakeContext(ctx)` на фоне: молчащий узел (принял TCP, не
отвечает на TLS) подвешивает `Read` рукопожатия на неограниченное время. Пока Tick висит:
- `Run()` перестаёт тикать (следующий тик ждёт возврата);
- `Status()` блокируется на том же мьютексе → HTTP API/GUI зависают;
- `Stop()` не спасает: cancel контекста Run не пробрасывается в `h.ctx`.
Фикс (три слоя): (а) пробам — `context.WithTimeout(h.ctx, probeBudget)` (дёшево 10с / дорого
15с); (б) выполнять сетевой I/O пробы **вне** `h.mu` (снапшот entry → probe →
lock → applyProbe), как это сделано в fxvpn/proton-сервисах; (в) `h.ctx` заменить на
контекст Run, пробрасываемый из Start.

### HIGH

**H1. Корни верификации узлов — системный пул, а не встроенный Mozilla/NSS.**
Дизайн §1.3: «VerifyConnection против реального имени с **встроенным Mozilla/NSS-пулом
корней** (цепочка заканчивается на USERTrust ECC CA)». Реализация
(`NodeDialer.resolveRoot`, dataplane.go:66) зовёт `x509.SystemCertPool()` с ленивым фолбэком
на пустой пул при ошибке. На OpenWrt/Entware без пакета `ca-certificates` системный пул
пуст → `opts.Roots` пуст → **каждый рукопожатие узла провалится** (`opera-dataplane-tls`),
туннель никогда не станет listening. Пустой пул после «успешного» разрешения — тихий
fail-closed без диагностики, который поле примет за «Opera не работает в моём регионе».
Фикс: embed пула корней (минимум — цепочка USERTrust ECC CA + AddTrust/Sectigo-корни, под
которые подписаны узлы sec-tunnel) в `transport/opera/assets/roots.pem`, слияние с системным
пулом, отдельный FailureClass `opera-dataplane-no-roots` при пустом итоговом пуле.

**H2. Дата-плейн диал без таймаута + carrier-failover без негативного кэша.**
`operaservice.failoverDialer` создаёт `net.Dialer{}` **без Timeout** и на каждый диал
пробует direct первым. При заблокированном direct (типичная РФ-ситуация, ради которой
существует carrier-режим) TCP-коннект уходит в чёрную дыру на ОС-таймаут (~2 мин на Linux):
каждый `DialStream` (и каждая проба супервизора!) платит 2 минуты до перехода на carrier.
Дизайн §2 обещает «гонку» и ступени; реализация — последовательный failover с
неограниченным первым этапом. Фикс: (а) `net.Dialer{Timeout: 5s}` в direct-этапе; (б)
негативный кэш прямого egress (после N подряд failures direct считается мёртвым на TTL 60с,
мьютекс-guarded); (в) для дешёвой пробы L1 — Use `ProbeCheap` только по carrier, когда
direct умер (экономия ресурсов carrier-туннеля тоже важна — сейчас дёшевая проба ходит
тяжёлым путём каждые 60с).

**H3. Bootstrap-стек устойчивости из дизайна §2 реализован на ~20%.**
Дизайн называет «главной силой протокола» и переносит «полностью»: гонка 9 DoH (+ dns/tls/tcp
схемы), фиксированный IP API, **цепочка api-proxy кандидатов** (до 15 параллельных полных
циклов register+discover), CSV-фолбэк эндпоинтов, авто-падение на локальный кэш при 801.
Реализовано: только direct + carrier-failover (одна ступень). Нет: DoH-гонки (DNS-этап
остаётся на системном резолвере — а DNS-фильтрация оператора как раз и отрезает
`api2.sec-tunnel.com`), api-proxy-цепочки, персистированного кэша узлов (дизайн: локальный
кэш как офлайн-актив; сейчас `h.nodes` — только память: после ребута с мёртвым API
listening не наступит, несмотря на живой carrier... carrier поднимет API, но discover
обязателен; без него список узлов пуст). Отдельно: **кэш узлов не персистится на диск** —
801-фолбэк «на локальный кэш» работает только внутри одного запуска. Фикс: минимально —
персистить последний успешный discover (по канону identity-слота) + TTL-мARK; при 801/отказе
API использовать его; отдельным этапом — DoH-резолвер гонкой (паттерн уже есть в
`transport/warp/doh.go` и `transport/dns/providers/race.go`!) и api-proxy-кандидаты.

### MEDIUM

**M1. JWT-обновление: неудача откладывает ротацию на полные 4 часа.**
`Tick` (health.go:303–310): при ошибке `RefreshCredentials` — `h.lastRefreshAt = now` и
возврат.Transient-сбой сети (или 429) оставит дату-плейн с протухающим JWT на 4 часа: все
новые CONNECT получат 407 (`opera-dataplane-connect-refused`) и уйдут в ротацию **узлов**
(нерелевантно — проблема в кредах). Дизайн §1.1: «установленные соединения не
затрагиваются» — да, но новые диалы умрут. Фикс: при неудаче ретрай с экспоненциальным
backoff от 60с до следующего каденса; классифицировать 407 на CONNECT как триггер
немедленного refresh (сейчас он не связан с refresh-циклом вообще).

**M2. 407-отказ дата-плейна не инвалидирует креды.**
`ClassDataPlaneConnectRefused` учитывается только в пробах как ProbeFail → ротация узлов. Но
407 = «прокси-креды отвергнуты», а не «узел плох». Ротация узлов при протухшем JWT — ложный
сигнал здоровья и лишний шум. Фикс: в `defaultProber`/`applyProbe` различать 407 (→
credsDead → registerFreshCapped, паттерн уже есть в `noteAPIFailure`) от прочих non-200.

**M3. Отсутствует observability-модуль.**
У fxvpn и proton есть `observability/fxvpn.go`, `observability/proton.go` (события+метрики в
`/metrics`). У оперы — ничего: ни `opera_dial_total{result}`, ни событий
`opera_established` (дизайн fxvpn §5 требует «строго после e2e-пробы = cutoff камуфляжа» для
всех новых транспортов), ни ленты событий для GUI. HealthStatus — единственная телеметрия.
Фикс: симметричный `observability/opera.go` (dial_total, probe_total{level,verdict},
restarts_total, discover_total, события established/rotated/refresh_failed).

**M4. `discover` не различает источники ошибки и не возвращает узел кэша при 801.**
Класс `ClassDiscoverRegionUnavailable` введён, но `health.discoverLocked` обрабатывает все
ошибки одинаково (rotаte → alternate/бэкофф). Специфика 801 («регион недоступен, работать
из кэша») не используется: смена региона может молча провалиться при живом кэше. Мелко, но
дизайн §2 п.5 прямо это требует.

**M5. Digest: профиль MD5-only — правильное следование дизайну, но без зонда.**
Если SurfEasy когда-нибудь переведёт API на SHA-256/MD5-sess, весь контрольный канал ляжет
с `ClassAPIAlgorithm` (структурный отказ — честно). Рекомендация: метрика/событие на каждый
случай `ClassAPIAlgorithm` (сейчас класс есть, наблюдаемости нет — см. M3) + задел
`opera-api-algorithm` в GUI-фейд. Не баг, а управляемый риск.

### LOW

**L1. `Run()` не делает первый тик сразу.** Первый Tick — через `CheapInterval` (60с):
бутстрап сессии начинается на минуту позже старта демона. fxvpn/proton зовут `r.tick(ctx)`
первым (service.go:280/383). Фикс — одна строка.

**L2. Relay глотает реальную ошибку направления при чистом EOF в другом** (dataplane.go:251):
`clean=true` → возврат nil, даже если `firstErr != nil`. Намеренная семантика, но стоит
задокументировать в godoc-строке рядом (для будущих читателей это выглядит багом).

**L3. `readConnectResponse` при `br.Buffered()==0` возвращает resp с неоткрытым Body** —
подключение утечёт к GC вместо явного close. Мелочь (Body = NopCloser не нужен... на самом
деле resp.Body не закрывается вовсе при этой ветке). Фикс: `resp.Body = io.NopCloser(conn)`
для единообразия.

**L4. `Client.RegisterNew` повторно использует `deviceRaw`** (per-Client device_hash). При
recovery-регистрации (auth refused) SurfEasy получит тот же device_hash → вероятно, вернёт
тот же device_id (семантика референса), т.е. «новая» регистрация может не быть новой. Не
критично (анонимная идентичность), но при `credsDead` надёжнее перевыгенерировать `deviceRaw`.

**L5. `swappableJar.Reset` создаёт jar с publicsuffix.List** — ок; но jar не привязан к
домену API… безопасно, это форм-API. Не баг.

**L6. `config.FakeSNI` не валидируется** как hostname (любая строка уйдёт в SNI).
Валидатор `validateOpera` проверяет region/control_target; fake_sni — нет. Фикс: RFC-1123
проверка по образцу `proton.ValidSNIName`.

**L7. Потоки дата-плейна без idle-таймаутов/лимитов** — туннель-коннект живёт пока жив peer;
watchdog движка покрывает на своём уровне. Отметить как принятый риск.

## 4. Что сделано лучше дизайна/референсов (сохранить при правках)

1. TOFU с pending→commit после доказательства канала — сильнее fxvpn-варианта (см.
   fxvpn-ревью F5) и сильнее всех upstream-референсов с InsecureSkipVerify.
2. Digest в 400 строк с golden-тестами и честной классификацией stale/refuse — красная линия
   §7.0 выполнена.
3. `errSetup`-маркировка локальных ошибок → ProbeCantBind не ротирует здоровые узлы —
   правильная трёхзначная логика.
4. Identity с перепроверкой деривации SHA1 и карантином — канон.
5. Антипетля на уровне сервиса (отказ self-loop по IP узла) — работает (в отличие от fxvpn,
   где гвард мёртв — см. fxvpn-ревью F6).

# 7. ГЛАВА: МАСКИРОВКА ОПЕРА ОТ ТСПУ (дизайн для реализации)

Цель — повторить для Opera (TCP/TLS-транспорт) то, что связка amnezia+анти-DPI даёт
awg-warp/awg-proton на UDP: **ТСПУ не должен отличить поток Opera от обычного браузерного
трафика и не должен получить устойчивые сигнатуры для глушилки**. Ниже — модель наблюдаемого,
разбор текущих сигнатур, конкретные механизмы (по возрастанию сложности), лестница
маскировки и план проверки. Всё проектируется под существующие механизмы b4x: pin-store,
packetmark, NFQ/action-планировщик, tlsgen, scoped-роутер.

## 7.1. Что видит ТСПУ сегодня (сигнатуры потока)

Поток Опера-дата-плейн = TCP до IP из известного диапазона SurfEasy (77.111.244.0/24 и
родственные, AS204954 и др.) на порт 443:

| Сигнатура | Сегодня | Насколько видна |
|---|---|---|
| SNI | Подавлен (пусто) по умолчанию; fake_sni опционально | **Высокая**: no-SNI TLS 1.3 — первый класс подозрений у ТСПУ, активно режется |
| TLS ClientHello отпечаток | Go crypto/tls (JA3/JA4 Go-стабильный) | **Высокая**: не совпадает ни с одним браузером; JA4-классификатор в арсенале ТСПУ штатный |
| ALPN | Отсутствует | Средняя: браузеры к CDN всегда предлагают h2/h3 |
| Сессионность | Каждый диал = полный хендшейк, нет resumption, нет session_id | Средняя: паттерн «робот», повторяющиеся full-handshake к одному IP |
| Поведение после CONNECT | Долгоживущий байтовый поток, бидирекциональный, без HTTP-семантики | Средняя при flow-analysis (объём/длительность/пакеты) |
| Диапазон адресов назначения | Фиксированные IP SurfEasy | **Высокая и неустранима на нашем уровне** (см. 7.6) |
| Контрольный канал | api2.sec-tunnel.com, TLS без SNI + Go-отпечаток | Высокая (но редкий, раз в 4ч) |

Ключевой вывод: **по сравнению с awg-warp Opera сегодня вообще не замаскирована** — ни
первого пакета-приманки (аналог amnezia I1), ни отпечатка браузера. Отсутствие SNI —
не «нейтрально», а прямо сигнатура.

## 7.2. Принцип переноса amnezia-семантики на TCP

Amnezia против DPI работает тремя вещами: (а) первый пакет потока — контролируемая нами
приманка (I1 = правдоподобный QUIC Initial), (б) мусор вперёд рукопожатия (Jc), (в) сам
хендшейк остаётся стандартным. Для TCP/TLS эквиваленты:

| Amnezia (UDP/WG) | Opera (TCP/TLS) — проект |
|---|---|
| I1-приманка «QUIC Initial с белым SNI» | **Fake ClientHello c белым SNI, умерший по TTL** (7.4.3) либо настоящий SNI узла (7.4.1) |
| Jc-мусор перед рукопожатием | Не применим к TCP (см. 7.4.3, почему нужен raw/NFQ) |
| Рукопожатие не трогаем | TLS-хендшейк не трогаем, но **задаём отпечаток** (7.4.2) |
| Лестница профилей + last-good | Лестница маскировки 7.5 |
| VanillaSafe-инвариант | Инвариант «pin-верификация не ослабляется маскировкой» (7.4.0) |

## 7.3. Конфигурационная модель (для реализации)

```
system.opera.masquerade {
  profile: "browser"        // browser | minimal | off (лестница 7.5)
  sni_mode: "node"          // node | pool | none (ДЕФОЛТ node — сейчас none!)
  sni_pool: []              // override встроенного пула white_sni (владелец)
  alpn: ["h2","http/1.1"]   // браузерный профиль
  session_resumption: true  // кэш TLS-сессий (7.4.4)
  ttl_fake: false           // NFQ-приманка c малым TTL (7.4.3, требует OUTPUT-хук)
}
```

## 7.4. Механизмы (реализуемые независимо)

### 7.4.0. Инвариант (обязателен)
Любая маскировка не ослабляет аутентификацию: VerifyConnection (pin для API, WebPKI+имя
узла для дата-плейна) остаётся единственным якорем доверия. Fake-SNI допустим только там,
где проверка не зависит от SNI: для контрольного канала — TOFU-пин уже независим от SNI
(готово!), для узлов — VerifyOptions.DNSName=реальное имя узла уже не зависит от SNI
(готово!). Это фундамент, на котором строятся 7.4.1–7.4.5.

### 7.4.1. SNI-дисциплина (первый шаг, тривиальный, максимальный эффект)
Инвертировать дефолт: `sni_mode=node` — в ClientHello идёт **настоящее имя узла**
(`eu0.sec-tunnel.com`): это легитимное имя CDN-класса, браузер Opera шлёт именно его.
`none` (сегодняшнее подавление) оставить как ЯВНУЮ опцию лестницы (последняя ступень, если
имя начнут резать по SNI). `pool` — SNI из пула белых имён (gosuslugi/sber/… по образцу
`proton/assets/white_sni.txt`, 90 live-tested имён): совместимо с pin-верификацией, т.к.
пин/VerifyOptions не смотрят на SNI. Реализация: `NodeDialer.FakeSNI` уже существует —
нужно только сменить дефолт в `operaservice.Build` и валидировать `sni_pool` (L6). Для
контрольного канала — та же опция в `buildAPITransport` (ServerName сейчас "" — заменить на
параметр; pin уже защищает).

### 7.4.2. Отпечаток ClientHello под браузер (главный механизм)
Цель: JA3/JA4 Opera-клиента == JA3/JA4 Chrome 128 (совпадает с заявленным UA
`OPR/114.0.0.0` → Chrome 128.0.0.0). Варианты по сложности:

- **(а) Тюнинг Go-конфига (недостаточно, но дёшево)**: CurvePreferences
  [X25519, P-256, P-384], полный браузерный набор cipher suites в браузерном порядке,
  signature_algorithms браузерный, ALPN [h2, http/1.1]. Убирает самые грубые отличия
  (Go шлёт мало-suite, странный порядок), но расширения/порядок остаются Go-шными —
  JA3 всё равно ≠ Chrome. Оценка: XS, делать обязательно как базу.
- **(б) uTLS (полное решение)**: vendored-fork `refraction-edge/utls` с
  `ClientHelloID.Chrome_128` — прецедент вендоринга форков в проекте есть
  (amneziawg-go v3). uTLS позволяет докрутить fingerprint побайтово. Проблема: красная
  линия «ноль новых зависимостей» — оформить как решение владельца (как для
  amneziawg-go/tor в прошлом), NOTICE-обновление. Реализация: `utls.UClient(rawConn,
  cfg, HelloChrome_120)` вместо `tls.Client` в `dialNodeTLS` + в `buildAPITransport`;
  VerifyConnection-callback у uTLS есть (поддержка кастомной верификации сохраняется).
  Оценка: M (с учётом вендоринга и тестов golden-JA3).
- **(в) Свой ClientHello-writer поверх crypto/tls-записей** — путь
  «tlsgen-расширить до полного рукопожатия»: tlsgen уже умеет собирать ClientHello с
  SNI-первым расширением (его основная фишка против ТСПУ!). Дополнить до завершения
  реального handshake (ServerHello-парсинг, key schedule TLS 1.3, record layer) — это
  ~2–3k строк и постоянная гонка с браузерными фичами. Не рекомендую: uTLS (б) дешевле
  и поддерживается сообществом.

Рекомендация: (а) немедленно, (б) отдельным этапом OP-M1 с явным решением владельца.

### 7.4.3. Приманка перед ClientHello — «amnezia-I1 для TCP» через штатный NFQ
Пользовательская TTL-приманка на живом TCP-сокете **невозможна без порчи потока** (фальшь
уйдёт по TCP-ретрансмиту с уже восстановленным TTL и разрушит стрим — известная ловушка).
Правильный путь — уже существующая в b4x инфраструктура:

1. Сокеты Опера-дата-плейн и API помечаются `SO_MARK = packetmark.MarkOperaEgress`
   (контроль через `net.Dialer.Control` — паттерн `transport/wg/socket_linux.go:35`
   готов, расширить `DialPolicy`/`NodeDialer.baseDialer`).
2. В `tables/iptables.go`/`nftables.go` добавляется правило OUTPUT mangle:
   `-m mark --mark <MarkOperaEgress> -j NFQUEUE --queue-num <action-queue>` —
   маршрут собственных исходящих потоков в существующий NFQ/action-планировщик
   (цепочки OUTPUT уже используются таблицами для DNS — инфраструктура зрелая).
3. Action-планировщик применяет к первому flight стратегии **fakedsplit / fakeddisorder**
   (action/strategy.go:15-16) с фейковым ClientHello из `tlsgen.GenerateTLSClientHello`
   (белый SNI, SNI-первым — его специализация) и низким TTL для фейк-части — ровно та
   семантика, что работает для WAN-трафика клиентов, теперь для собственных потоков.
4. Правило отключается при `masquerade=off` и не создаётся, когда NFQ-движок не активен
   (честный статус в observability).

Это и есть «штатные средства анти-DPI b4x» в чистом виде — переиспользуем fakedsplit и
планировщик, а не изобретаем per-transport обфускацию. Оценка: M. Риски: конфликт с
существующими OUTPUT-правилами DNS (тестируется юнитом таблиц + полевым смоуком);
само-петля (marked-пакеты не должны повторно попадать в NFQ — решение: exempt-mark
после обработки, как в существующем конвейере).

### 7.4.4. Сессионность и ресампшн
- `tls.Config.ClientSessionCache` (newSessionCache per node host) — второе и последующие
  соединения к узлу идут с resumption (1-RTT, session_id непустой) — браузерный паттерн.
  Совместимо с VerifyConnection (пин проверяется и на resumed-хендшейке).
- ALPN `h2, http/1.1`: SurfEasy-узлы — TLS-терминаторы CDN; предложение h2 делает hello
  браузерным. Если узел согласует h2 — сейчас CONNECT-движок speaks HTTP/1.1: тогда
  **принудительно оставить в конфиге NextProtos=["http/1.1"]-only** для дествующего
  движка, а h2-CONNECT (одна долгоживущая сессия с мультиплексом стримов, паттерн
  fxvpn `h2tunnel.go`!) — это одновременно и **производительность** (сейчас каждый диал
  = новый TCP+TLS+CONNECT хендшейк = handshake-burst сигнатура) и маскировка
  (браузер держит мало долгоживущих соединений). Этап OP-M2: H2-CONNECT-сессия для
  Opera поверх существующего digest/pin-стека. Если поле покажет, что узлы не дают h2 —
  остаёмся на http/1.1 с честным статусом.

### 7.4.5. Контрольный канал
- SNI: реальное имя `api2.sec-tunnel.com` (дефолт) или pool; **TOFU-пин делает fake-SNI
  безопасным** — сейчас уже реализована схема «ServerName-независимая верификация»
  (VerifyConnection смотрит только пин). Меняется один конфиг-параметр.
- Тот же uTLS-профиль Chrome (б), тот же ALPN.
- Редкий трафик (раз в 4ч) — не добавляет шума.

### 7.4.6. Что НЕ делать
- Пейсинг/шейпинг даты-плейна под «браузерность» — дорого и бессмысленно: ретрансмиты и
  алгоритмы контроля насыщения всё равно выдадут нас по мелким статистикам; фокус на
  первых flight (DPI-классификаторы ТСПУ принимают решение на хендшейке, flow-эвристики —
  на порогах объёма, которые не победить тюнингом).
- Fake-QUIC поверх TCP-потока — бессмыслица; не смешивать UDP-паттерны amnezia с
  TCP-транспортом.

## 7.5. Лестница маскировки + last-good (аналог Seeker'а wg)

Лестница по убыванию маскировки/по возрастанию совместимости, с персистентным last-good
(канон `twg.LastGoodStore`):

```
[ browser+node-SNI+ALPN+resumption ]     # полная маскировка
  → [ browser+pool-SNI ]                 # имя узла начали резать по SNI
  → [ browser+no-SNI ]                   # пул тоже в блоклисте
  → [ plain-Go + node-SNI ]              # uTLS-слой сломался/откат
  → [ today: plain-Go + no-SNI ]         # текущее состояние — последняя ступень
  + [ ttl_fake/NFQ-приманка ]            # независимый ортогональный слой
```

Триггер шага вниз — подтверждённые классы отказов (CONNECT-timeout на новых сессиях при
живом TCP-диале, RST-шторм после ClientHello) через существующий детектор блокировок
(`src/detector`, adaptive discovery). Шаг вверх — только по cooldown (анти-осцилляция,
канон fxvpn `ladder.go`: один эпизод = один свитч). События `opera_masquerade_switched`
в observability.

## 7.6. Ограничения, которые маскировкой не лечатся (зафиксировать честно)

1. **IP-репутация SurfEasy**: диапазоны 77.111.244.0/24 и соседние — публично известные
   «Opera VPN». Блок по dst-IP/AS обходит любую маскировку. Ответ программы — существующий
   carrier-режим: дата-плейн оперы через активный базовый туннель (сейчас carrier-failover
   есть и на дата-плейне — `NodeDialer.Next` → `c.opts.DialContext`). Рекомендация:
   конфиг-режим `data_plane_route: auto|carrier-always` — при обнаружении IP-блока
   (детектор: TLS-RST от всех узлов) включать carrier-always без смены маскировки.
2. Квоты/блокировка на стороне Opera (глобальный бан infra) — вне нашего контроля.
3. UDP-эгресса нет у протокола — Opera никогда не будет full-scope (задокументировано).

## 7.8. Красные линии главы

1. Pin/WebPKI-верификация не ослабляется НИКОГДА (7.4.0) — маскировка меняет только
   наблюдаемые байты, не модель доверия.
2. uTLS — только явным решением владельца (вендоринг = исключение из красной линии
   зависимостей, обновление NOTICE).
3. NFQ-приманка не применяется к контрольному каналу через carrier (двойная обфускация
   вложенных туннелей = маркер сам по себе).
4. Лестница без осцилляций: один эпизод — один шаг, cooldown 300с (канон программы).
5. Все ступени наблюдаемы: события переключения обязательны, silent-fallback запрещён
   (канон программы).
