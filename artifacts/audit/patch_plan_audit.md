## Топ-5 проблемных stages

1. **Stage 17 (planner, A)** — nfq использует из `action` только `ActionTokenStore`; планировщик (planner/markers/packet_builder) и executor существуют как библиотека с тестами, но production-инъекции по-прежнему идут через legacy-пути (`nfq/extsplit.go`, `desync.go`, `combo.go`, `firstbyte.go`, `disorder.go`). Core Fix «stream-offset planner» фактически не подключён.
2. **Stage 19 (executor fail-safe, A)** — executor не вызывается из production; raw-send/checksum-валидация размазана по legacy-коду nfq+sock. DoD «centralized packet builder» не выполнен в графе.
3. **Stage 36 (field validation, B)** — `src/fieldtest` (27 файлов) не импортируется ни одним пакетом (unwired, standalone), тестов 1 на файл (session_test.go); 14 Android-сценариев и success-metrics не автоматизированы как тест-сюит.
4. **Stage 33 (TUN/SOCKS fallback, C)** — `routing.FallbackManager` подключён к `nfq` через authorized transactional route path (FB-23, b4x-jsd: `nfq/route_binding.go:52` после exact-flow Bind; конвертер `nfq/fallback_route.go`; GC в pool ticker), но TUN/SOCKS-адаптеры, применяющие SO_MARK/rule metadata, по-прежнему отсутствуют — применение решения на устройстве остаётся открытой работой.
5. **Stage 28/29/31 (Level C strategies)** — все три реализованы на уровне библиотеки `action` (PlanHostFakeSplit/PlanFakeMix/PlanTLSRecordSplit/каталог multisplit) с fuzz/bench, но ни одна не вызывается из NFQ-пути — это согласуется с планом (Level C после Core Fix), но статус «реализовано» не означает «в проде».

## Примеры расхождения кода с описанием stage

1. **Кодировка аудита (Stage 1)**: план требует `docs/audit/b4-1.73-flow-path.md`, файл есть, но записан в cp866 — кириллица нечитаема в UTF-8-окружении (сам PATCH_PLAN при этом UTF-8, вопреки вводной о cp866).
2. **Stage 17 vs реальность**: в плане «Перевести существующие B4 fake/split/combo actions на planner» — фактически legacy-техники (extsplit/desync/combo/firstbyte/disorder + `sendFakeSyn` в `nfq/syn.go`) продолжают существовать и работать без planner; планировщик живёт изолированно в `action/` (только библиотечные вызовы из hostfakesplit/fakemix/tlsrecordsplit).
3. **Stage 32/36 (RST)**: план требует «TCP SYN traceroute» и controlled RST с packet-path корректностью — активная часть (traceroute, active RST) реализована только в unwired `fieldtest/rst.go`; в production (nfq) есть лишь пассивный RST-path мониторинг/подавление, т.е. половина DoD недостижима из runtime.
4. **Stage 30 «auto-selection»**: bounded auto-selection формально обеспечена конфигом (MaxShadowProbes, StableSuccesses, NoAutomaticApply), но `RunAdaptiveMatrix` вызывается только из тестов — из discovery-рантайма прямое использование не подтверждено (может быть расхождением или недоаудитом).

## Методология и ограничения

- `go list -deps ./` выполнить нельзя: `go` не установлен на хосте (Windows). Связность установлена статическим анализом импортов (список импортов каждого пакета прочитан из исходников).
- Тесты НЕ запускались (read-only аудит, Go недоступен); колонка «Тесты» = наличие *_test.go/функций Test/Fuzz/Benchmark по grep, не факт их прохождения.
- Кодировку PATCH_PLAN проверил по байтам: UTF-8 (`D0 9F` = «П»), cp866 — ошибочная вводная; вся кириллица прочитана корректно.
