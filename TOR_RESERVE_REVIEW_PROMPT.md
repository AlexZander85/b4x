## 0. Роль и мандат

Ты — строгий ревьювер резерва E-TOR (Tor-туннель для роутера b4x). У тебя два
объекта, которые ты оцениваешь РАЗДЕЛЬНО, и один выходной артефакт — план
доработок и улучшений.

1. **Дизайн** (`tor-reserve-design.md`, v1) — оценить как архитектурный документ:
   полнота, верифицируемость утверждений, соблюдение красных линий проекта,
   реалистичность на целевом железе (Keenetic/Entware, MIPS/ARM, CGO=0,
   GOMEMLIMIT от 32 МБ), покрытие всех видов входов, качество инноваций
   (mixed-set racing, egress-мост, vanilla-through-carrier, NFQ-bait).
2. **Реализация** (ветка `agent/classifier-v2.3-capture-envelope`, HEAD и
   коммиты после `3525acf`) — оценить против патч-плана
   `tor-reserve-patch-plan.md` (этапы TT1–TT10): покрытие, инварианты,
   тесты, регресс.

Если реализация ещё не начата (коммитов с кодом TT-этапов нет) — выполни
только часть A (дизайн) и явно скажи это в вердикте; план доработок тогда
касается только дизайна. Если реализация частичная — ревьюишь что есть,
отсутствующее помечаешь как GAP с этапом-владельцем.

## 2. Часть A — ревью дизайна (всегда)

### A.1 Верифицируемость фактов
Дизайн утверждает факты о внешнем мире (§1) со ссылками на research-отчёты.
Выборочно перепроверь ≥10 утверждений против research-файлов (и против
исходников в `/home/z/refs/…`, если доступ к клонам остался; иначе против
памяти отчётов): байтовые константы пробы релея (VERSIONS/NETINFO/CREATE/
CREATED), бюджет 510 Б SOCKS-аргументов, директива `Socks5Proxy` и её покрытие
(все ли соединения tor уходят через неё — включая Dir-соединения?), поведение
`SETCONF ConfluxEnabled` на tor без conflux, версия utls. Каждое расхождение —
находка CRITICAL (дизайн на неверном факте = реализация на песке).

### A.2 Красные линии
Пройди по списку design §12 (11 пунктов) и красным линиям proton-awg-design
§10. Ищи: нарушения, которые дизайн допускает молча; места, где «исключение из
красной линии ноль зависимостей» разползается шире §10; bait/NFQ-механика,
которая может включиться неявно; антипетли, которые не покрывают все категории
(bootstrap-источники, рандеву, DoH, control); UDP-пути.

### A.3 Инновации — стресс-тест логики
Для каждой из четырёх ключевых разработок ответь «сломается ли, и что тогда»:
1. **Mixed-set racing (§2.1)**: что если tor в mixed-set выберет мост, который
   проба не считала живым? Как атрибутируется winner при >1 мосте одного
   транспорта? Конфликт между RaceWindow и memory?
2. **Egress-мост (§3)**: Socks5Proxy не покрывает PT-соединения (они идут через
   in-process PT-прокси) — не возникает ли ДВЕ точки egress с разной политикой?
   Куда попадает DoH-резолв hostname-мостов (§3.2)? Диалер `auto` и
   bootstrap-источники: нет ли петли «tor ищет мосты через tor»?
3. **Vanilla-through-carrier (§2.2)**: что происходит с цепочками при смерти
   носителя — действительно ли «разрыв», а не «висящие TCP»? Self-loop: носитель
   = tor сам (kind=tor через kind=tor) — где гарантия?
4. **Relay-scanner (§4.3)**: глубокая проба = активное зондирование чужих
   релеев CREATE-ячейками — оценка риска IDS/абьюза, бюджеты достаточны?

### A.4 Реалистичность платформы
MIPS: pion/webrtc (snowflake) — память/CPU; дизайн имеет запасной план §14
патч-плана (build-tag tor_snowflake), но он «согласовать до TT5» — оценена ли
цена этого решения честно? Размер vendor (+pion/KCP) на mips-образах; FD-бюджеты
(история FD-утечек проекта); /tmp 243 МБ vs data/ на /opt (флешка, износ,
AvoidDiskWrites — противоречия?).

### A.5 Полнота против постановки владельца
Требование: «все виды входов по типу Nova» (webtunnel, vanilla, obfs4,
webtunnel, snowflake, meek_lite…) — сверь каталог design §2 с ENTRY_MODES
Nova (research-nova-tor §C): все ли входы Nova покрыты; прямое указание
владельца на meek/conjure/dnstt — дизайн их «распознаёт, не подключает» —
достаточно ли это (или нарушение постановки — вопрос для эскалации, не для
тихого решения).

## 3. Часть B — ревью реализации (если код есть)

### B.1 Карта покрытия этапов
Таблица: TT1–TT10 → статус (не начат / частично / завершён) → DoD выполнен?
Каждый DoD-пункт из патч-плана — сверка с фактическими тестами (названия
тест-функций). Матрица §12 патч-плана (24 сценария) — какие покрыты, какие
нет.

### B.2 Инварианты (проверять по коду, не по словам)
1. **Никакой утечки мимо носителя** (egress.through=<kind>): найти в коде ВСЕ
   пути `net.Dial`/`net.DialContext` в src/transport/tor/ — каждый обязан
   проходить через egress-диалер; прямой диал где-либо = CRITICAL.
2. **Bootstrap-источники никогда через tor**: collector/Moat/onionoo-диалы.
3. **Self-loop guard**: carrier.DialStream на слушатели tor; PT-ACL (чужая
   цель → 0x02); egress-мост с кредами.
4. **enabled=false → ноль горутин/слушателей/файловых записей** (тест есть?).
5. **Shutdown-порядок**: Unregister ДО Stop; тор-процесс умирает (owning
   controller); PT-прокси гасится после tor; без сирот.
6. **Бюджеты**: restartGuard 6/ч; страйки мостов; bounded-лимиты соединений;
   event ring 32; серии метрик bounded.
7. **Парсер bridge-строк**: инъекция `\n`/`\#"`/CRLF; бюджет 510 Б; sqs-отказ;
  Decoration-адреса не диалятся. Тест-кейсы из §3.1 патч-плана фактически есть?
8. **Таксономия**: события snake_case, классы kebab, метрики `tor_` — по коду.
9. **Consent rule**: ни одного живого сетевого вызова в юнит-тестах (искать
   реальные URL/IP в _test.go; httptest-стенды — ок; env-гейт
   B4X_TOR_INTEGRATION — ок).
10. **Зависимости**: go.mod/vendor = перечень design §10; aws-sdk-go-v2 в
    vendor отсутствует (SQS-вырезание); replace tools/snowflake указан; патч
    содержит ровно 2 класса изменений.

### B.3 Качество кода против канона проекта
Сверка с protonservice-каноном: инжектируемые now/диалеры; sentinel-ошибки;
честные состояния (binary-missing с подсказкой, а не ошибка сборки);
`Effective*()`-паттерн конфига; AtomicFile-канон стора; nil-safe handlers;
swagger-аннотации; graceful degradation (conflux SETCONF 5xx → событие, работа
продолжается).

### B.4 Тесты
`go vet ./... && go test ./... && go test -race ./...` — запустить, зафиксировать
вывод. Регресс существующих суит = 0. goleak в новых пакетах. Интеграционные
гейты (B4X_TOR_INTEGRATION) — skipped без бинаря, это норма; отметить.

## 5. Критерии качества самого ревью

- Каждая находка — с file:line или design §N. «Мне не нравится» — не находка;
  «инвариант X нарушен в Y, потому что Z» — находка.
- Найди ≥1 слабое место в каждой из четырёх инноваций (если его нет —
  докажи устойчивость явно). Ревью без находок CRITICAL/HIGH по коду из
  ~5-8K строк — повод перепроверить глубину.
- Не предлагай новых зависимостей. Любое предложение — в рамках stdlib +
  существующего vendor + перечня design §10.
- Все улучшения — с учётом платформы: MIPS, память, флешка, FD-лимиты.
- Проверь согласованность дизайн ↔ патч-план ↔ код: номер §, имена
  состояний/событий/метрик, значения таймаутов не должны расходиться.
- Явно ответь на вопрос владельца: **готов ли E-TOR к полевому прогону
  FIELD_TEST_TOR_PROMPT.md, и если нет — какие P0 закрывают путь**.

## 6. Красные линии ревьюера

1. Не менять код/документы (только создать tor-reserve-review.md).
2. Не запускать живые сетевые запросы из тестов; тесты запускаются только
   как есть (unit/httptest).
3. Не деплоить на роутер; полевой этап — отдельный агент.
4. Если обнаружена дыра безопасности/приватности (утечка DNS, обход
   egress-моста, инъекция torrc) — это CRITICAL независимо от этапа.
5. Отчёт честный: «не нашёл» ≠ «нет»; сомнения фиксируй как OPEN-вопрос.
